01

El Problema de los 7 Días

Supabase opera sobre infraestructura PostgreSQL en contenedores independientes. Para optimizar recursos en su plan gratuito, aplica una política estricta de 168 horas (7 días) de inactividad continua. Si una base de datos no recibe peticiones durante ese lapso, la instancia se apaga (Paused state).

⚠️ Consecuencia: Cold starts de 30-45 segundos o errores 503 en la primera petición de tus usuarios.
02

Mecanismo de Latido Supalive

Supalive envía peticiones HTTP autenticadas con encabezados apikey y Authorization: Bearer a la capa PostgREST. Al procesar la firma del token criptográfico y consultar el catálogo interno de PostgreSQL, el contador de inactividad se reinicia a cero.

✅ Garantía: Frecuencia de 12 horas = 14 latidos semanales (13 latidos de margen de seguridad).
03

Arquitectura Zero-Trust

Las credenciales residen en GitHub Secrets (encriptación asimétrica Libsodium) y variables de entorno seguras de Vercel. El cliente público nunca recibe la URL completa ni las claves API: todos los identificadores son enmascarados criptográficamente.

🔒 Seguridad: El repositorio y el showcase son 100% públicos sin riesgo alguno de fuga.

Flujo de Ejecución del Latido

Paso 1 · Cron Disparador

GitHub Actions Scheduler

Paso 2 · Carga Cifrada

Inyección de Secrets

Carga el arreglo JSON de proyectos desde secrets.SUPABASE_PROJECTS con enmascaramiento.

Paso 3 · Petición HTTP

PostgREST Gateway

Fetch autenticado a /rest/v1/ con API key. Despierta el pooler de PostgreSQL.

7 Días ➔ 0 Días
